# Upgrade from the existing Windows application

The legacy-compatible handoff remains a test migration until the native application and migration have passed production qualification. A test release must clearly identify its limitations; the legacy updater may offer prereleases.

The deployed Python application's updater selects an official GitHub release asset named `MeshCore-Command-Windows-<version>-Setup.exe`, checks its GitHub SHA-256 and size, then launches it with `--update <pid>`. The native test installer accepts that handoff and is published as a prerelease, but is not a production-qualified replacement. The native updater uses its own asset name and `--native-update` handoff, which remains distinct.

The development installer uses a PID-only legacy wait helper that verifies the executable path, waits without terminating it, and rejects a mismatched process. A PID-only handoff cannot carry the old process start time, so profile and installation locks remain necessary.

The development installer parses the legacy `--update <pid>` arguments and orders the transaction: wait for the old process, check that another legacy executable is not running, check for conflicting native credentials, prepare the native installation, start the candidate, confirm readiness, and only then switch recognised shortcuts while retaining backups. It checks again after preparation and before switching shortcuts if the old app has reopened. These checks reduce the race but cannot prevent a new old-app instance from starting immediately afterward. If a candidate profile exists, the installer validates its selection and independent credential marker and explicitly offers to use it without merging. Declining leaves both profiles and shortcuts unchanged. Credential preflight reads both stores but does not modify them; the candidate checks again while copying. Synthetic tests cover the ordering and a disposable handoff; they do not establish feature parity or qualify a release.

A startup-receipt helper supports an atomic, one-time nonce receipt with timeout and mismatch checks, and detects a process exiting before producing it. Both native and legacy development update paths wait for a receipt after profile selection, credential isolation, loading the shell and desktop bridge, and comparing a digest of copied localStorage records before and after shell startup, excluding volatile radio session and lease keys. These checks do not establish that every setting is usable. The old program must remain available until the end-to-end path is verified.

The native window checks that the shell and desktop API bridge are present. The synthetic integration mode writes a nonce receipt only after that check and the synthetic checks complete; the build validates it in a temporary directory. For an upgrade, the candidate also verifies selected copied records before issuing its receipt.

The disposable native installer update test waits for the test window's receipt and successful exit. A separate disposable legacy handoff test exercises installation, a packaged synthetic candidate window and receipt, shortcut backup and switching, and a simulated startup failure. An opt-in copied-profile audit also verifies the real legacy credentials against an in-memory destination and runs the packaged installer and candidate migration against a disposable copy of the development PC's profile and test shortcuts; that check passed. The candidate migration uses synthetic credentials. It does not write the real native credential store or alter the real installation. The compatible handoff is published as a test update and requires broader end-to-end validation.

The native preview updater restores the previous version if startup fails and the candidate has exited. If the candidate might still be running, it avoids switching versions underneath it. Rollback checks both installation pointers under the installation lock and refuses to overwrite a concurrent change. A shell-readiness receipt does not by itself prove migrated data is usable.

The test release provides both the legacy-compatible asset name and the native updater's expected asset name, each pointing to the same installer handling the corresponding handoff. For future releases, confirm the installer fits the legacy updater's 200 MiB limit and carries the correct version, and check the published metadata and digest. GitHub's digest is not an independent signature. More real-world update testing is needed before a production release.

The migration must wait for the old process and its profile locks to release, stage and verify the native installation separately, and copy the existing WebView profile and local data while retaining the loopback origin. Preserve credential references and any external map dependencies. Do not remove or overwrite the original profile, local settings, messages, maps, credentials, or the old executable until the migrated app has started successfully and its data has been verified. Keep an accessible rollback path if migration, startup, or verification fails. Because the two profiles are separate after copying, do not silently switch back and forth or merge them without an explicit, tested reconciliation process.

After readiness and shortcut switching, the installer moves the old program directory to a uniquely named sibling under LocalAppData. This removes it from its installed location while retaining a rollback copy; settings, messages, maps and credentials are stored separately and are not deleted. If retirement fails, the native app remains available and the installer reports that the old program is still in place. Exercise success, cancellation, locked-profile, interrupted-install, incorrect-package, and failed-startup scenarios using copies and disposable installations before treating the upgrade as production-ready.
