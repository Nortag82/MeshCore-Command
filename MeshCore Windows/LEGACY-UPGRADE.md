# Upgrade from the existing Windows application

This is a release plan, not an enabled migration. Do not publish a native installer under the legacy asset name until the native application and migration have passed production qualification.

The deployed Python application's updater selects an official GitHub release asset named `MeshCore-Command-Windows-<version>-Setup.exe`, checks its GitHub SHA-256 and size, then launches it with `--update <pid>`. Existing installations cannot be changed retroactively by editing the repository. The development installer now accepts that handoff, but has not been qualified or published as a replacement. The native updater uses its own asset name and `--native-update` handoff, which remains distinct.

The development installer uses a PID-only legacy wait helper that verifies the executable path, waits without terminating it, and rejects a mismatched process. A PID-only handoff cannot carry the old process start time, so profile and installation locks remain necessary.

The development installer parses the legacy `--update <pid>` arguments and orders the transaction: wait for the old process, check that another legacy executable is not running, prepare the native installation, start the candidate, confirm shell readiness, and only then switch recognised shortcuts while retaining backups. It refuses an existing candidate profile because it cannot safely merge divergent data. Synthetic tests cover the ordering and a disposable handoff; they do not establish feature parity, prove migrated data usable, or qualify a release. Profile locks are still required because a new old-app instance could start after the process check.

A startup-receipt helper supports an atomic, one-time nonce receipt with timeout and mismatch checks, and detects a process exiting before producing it. Both native and legacy development update paths wait for a receipt after profile selection, credential isolation, loading the shell and desktop bridge, and comparing a digest of selected copied message, secure-contact, monitoring and map records before and after shell startup. These checks do not establish that every setting is usable. The old program must remain available until the end-to-end path is verified.

The native window checks that the shell and desktop API bridge are present. The synthetic integration mode writes a nonce receipt only after that check and the synthetic checks complete; the build validates it in a temporary directory. For an upgrade, the candidate also verifies selected copied records before issuing its receipt.

The disposable native installer update test waits for the test window's receipt and successful exit. A separate disposable legacy handoff test exercises installation, a packaged synthetic candidate window and receipt, shortcut backup and switching, and a simulated startup failure. An opt-in copied-profile audit also verifies the real legacy credentials against an in-memory destination and runs the packaged installer and candidate against a disposable copy of the development PC's profile and test shortcuts; that check passed. It does not write the real native credential store or alter the real installation. The source handoff has not been published as a compatible update or verified end to end with a real legacy installation.

The native preview updater restores the previous version if startup fails and the candidate has exited. If the candidate might still be running, it avoids switching versions underneath it. Rollback checks both installation pointers under the installation lock and refuses to overwrite a concurrent change. A shell-readiness receipt does not by itself prove migrated data is usable.

For a future release, provide both the legacy-compatible asset name and the native updater's expected asset name, each pointing to a verified installer that handles the corresponding handoff. Before releasing, confirm the full installer fits the legacy updater's 200 MiB limit, carries the correct version, and is trusted according to the release's package-authenticity policy. Test the actual published GitHub metadata and download, including its digest and redirects, from an existing installed version.

The migration must wait for the old process and its profile locks to release, stage and verify the native installation separately, and copy the existing WebView profile and local data while retaining the loopback origin. Preserve credential references and any external map dependencies. Do not remove or overwrite the original profile, local settings, messages, maps, credentials, or the old executable until the migrated app has started successfully and its data has been verified. Keep an accessible rollback path if migration, startup, or verification fails. Because the two profiles are separate after copying, do not silently switch back and forth or merge them without an explicit, tested reconciliation process.

Only after the new installation and migration are verified should the release offer to remove the old program files and replace the shortcuts. Removal must leave user data and rollback material intact. Exercise success, cancellation, locked-profile, interrupted-install, incorrect-package, and failed-startup scenarios using copies and disposable installations before enabling this upgrade for users.
