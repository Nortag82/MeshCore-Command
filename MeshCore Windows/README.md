# Windows native migration (in progress)

This directory contains the C# replacement for the Python desktop host. Native Windows 2.0.43 is the current Windows release and includes a legacy-upgrade path. User testing has covered migration, backups, radio use, messaging and maps, flashing and installation; results are not a guarantee for every hardware configuration.

See the [experimental HFLink guide](../docs/HFLINK.md) for the native direct-messaging workflow, no-RF simulation and Mercury setup.

The .NET 10 core includes companion stream framing, acknowledged queues, Wi-Fi discovery and reconnect, USB serial, a Windows Bluetooth GATT adapter with authenticated pairing, profile and credential compatibility, GPS input, offline map access and verified-helper map downloads. It also includes compatible encrypted backup, snapshot, validation and rollback code, firmware preflight checks, and installer release/download validation. The local endpoint supports radio frames, credentials, notifications, elevation and offline maps. Hardware transports, notifications, real map downloads and the desktop backup workflow require physical and end-to-end testing. Firmware flashing, update installation, production data migration, and other desktop API features are not complete.

Once a Wi-Fi board has been identified, reconnect verifies that the radio at the saved address still has the same public identity before exposing the connection. Retry delays increase when short-lived connections repeatedly close; this limits rapid retries when another client is competing for the radio. Loopback tests check backoff, rejection of a different identity and preservation of frames received during a valid reconnect. On the spare Heltec V3, a forced reconnect verified the same identity and a fresh battery response; a separate three-minute interface observation had no disconnected samples or transport closures when it was the only connected client. Longer runs and other supported boards remain to be qualified.

`MeshCore.Windows.Preview` runs the existing web interface in an isolated temporary profile on port 19484. Radio access is disabled by default; the development-only `--enable-experimental-radio` switch allows manual testing, can interrupt another client of the same radio, and may consume messages queued on the radio into temporary data. Use only a dedicated test radio. The separate `--enable-experimental-flash` switch exposes an unqualified flasher and must only be used for dedicated hardware testing. This preview uses temporary in-memory credentials, not the production credential store, and must not be used as a replacement. `--smoke-test` and `--integration-test` check startup and a synthetic board without showing a window or connecting a radio; `--ble-scan-test` scans for nearby MeshCore BLE devices without connecting.

The experimental flasher uses the Rust [espflash 4.7.0](https://github.com/esp-rs/espflash/tree/v4.7.0), distributed under MIT or Apache-2.0. `Fetch-EspFlash.ps1` retrieves and verifies its pinned Windows x64 release before a preview build. It is not checked into the repository. The flasher must be qualified against each supported board and its USB provisioning path before release.

The native shell and icon are maintained under `MeshCore Windows/assets`. Firmware images are generated files and are not included in the source checkout: stage the complete image directory under `MeshCore Windows/firmware`, or set `MCC_FIRMWARE_DIR` to its absolute path. The build checks that all listed images and the manifest exist, and the packaged application verifies their hashes before flashing. Building the firmware images themselves still requires the firmware toolchain and source.

The migration staging code copies a closed WebView2 profile and desktop data into a separate directory, checks copied files and board profiles, and leaves an incomplete marker on failure. It adjusts a selected offline map path when the map was inside the copied data directory; maps selected outside that directory remain external dependencies. A synthetic WebView2 test stages a profile and opens the app at the same origin. The published test installer supports the legacy handoff described in [upgrade notes](LEGACY-UPGRADE.md); this path still needs wider verification.

The native profile registry selects a successfully staged profile with an atomic pointer, preserves its loopback port, and reuses that profile on later starts. It rejects incomplete data, invalid pointers and simultaneous migration attempts. It also supports explicitly creating a fresh profile without replacing an existing selection. The app integration test exercises both paths with synthetic data. An explicitly invoked `--native-candidate` development path connects a copied profile and exposes the experimental flasher. The isolated preview installer offers a separate button to open this candidate; it must not be treated as a production migration. After a copy, changes made in the old and candidate apps are not merged. Published preview 0.1.1 shares its credential store with the old app; the development source changes this as described below.

The preview's separate synthetic integration test seeds a saved conversation for a simulated radio, then checks that the view shows both the saved history and a newly received message. This does not test migration of actual user data.

Message popups respect channel and direct-contact mute settings, including during initial radio synchronisation. Muted messages remain in local history; contact mute also suppresses Secure Coms message popups.

Channel messages have an unverified display name, not a verified sender key. The message context menu can open a uniquely named saved chat contact after confirmation, or import a MeshCore contact-card link provided separately by the sender. The importer checks the packet structure, asks the user to compare the public key, and reports success only when the connected radio lists that key. A flood advert is another way to discover a contact.

Secure messages are limited to 74 UTF-8 bytes. The individual and group composers show an inline warning with the excess byte count when a draft is too long; the limit has not changed.

The native window's fullscreen control and F11 now use a borderless view on the current monitor, restoring the previous window position and state when toggled off. A preview integration check exercises the control through the desktop bridge; fullscreen and multimonitor behaviour still need interactive testing on different display setups.

The optional `--audit-legacy-profile` developer check makes a temporary, hash-verified copy of a closed legacy profile, reports only aggregate counts and whether corresponding secure credential entries exist, then removes the temporary copy after WebView2 closes. It does not connect a radio or print message contents, names or secrets. It requires the original local origin to be free and does not itself install or migrate user data.

The audit also verifies the real legacy credential-copy logic against an in-memory destination without changing or printing the saved credentials. It opens the disposable profile in native candidate mode with radio access disabled, then compares selected message, secure-contact, monitoring and map records and the saved-board file before and after. An optional installer check runs the packaged upgrade against that copied profile and disposable shortcuts; its candidate performs a second profile migration using synthetic credentials. These checks passed on the development PC. They do not test every setting, write the real native credential store, or upgrade the real user profile.

The installer core verifies and stages a package under a version directory, retains the prior version and can switch its pointer back. The native update selector accepts only assets named `MeshCore-Command-Native-Windows-<version>-Setup.exe`. An installed candidate checks GitHub and verifies the published SHA-256 digest; the installer waits for the parent process and profile lock. A simulated update tests the installer and rollback in temporary directories. Native test installers have been published, but signing and broader real-world update testing remain outstanding. GitHub's digest detects mismatched downloads; it is not an independent signature.

`Build-Native-Installer.ps1` builds the test installer with embedded files and an explicit preview label. Its automated tests exercise the versioned launcher and disposable installations. The legacy `--update` path can copy a profile or, with confirmation, use an existing native profile; after a readiness receipt it switches recognised shortcuts and moves the old program to a recovery folder. This is published as a test update, not a production-qualified replacement. When the same preview version is already installed, setup offers to open it instead of reinstalling it.

Setup can optionally create a separately named Start menu shortcut for the native candidate. It does not replace an existing shortcut with the same name. The installer test creates and checks a shortcut only inside its disposable test directory.

The installer version comes from `NativeVersion.props`; the build checks the executable's embedded version against that file. The update handoff refuses an installer whose embedded version differs from the release selected by the app.

The preview records unhandled-error categories, exception types, error codes and application method names under its temporary `Logs/crashes.log`. The native candidate instead keeps its log under `%LOCALAPPDATA%\MeshCore Command Native Candidate Data\Logs\crashes.log`, so it survives a restart. It deliberately excludes exception messages, arguments and source paths because they can contain passwords, message text or local paths. This is not yet integrated into the production support workflow.

Desktop message alerts use an app-drawn, non-activating popup as the Windows tray balloon did not appear during testing on the target PC. A local synthetic popup was visually confirmed there. A simulated radio message is tested through the actual web interface and notification endpoint, including its generic alert text. In a separate test, a Public channel message sent from a second physical radio arrived at the spare V3 and the user confirmed seeing the popup; the first message's popup was not observed, so further reliability testing is still needed. These popups are not Windows Action Center notifications. Secure alert text must remain generic; a real Secure Coms notification still needs qualification.

An automated Secure Coms receive test checks that an authenticated message requests a generic alert without plaintext and that a replay does not trigger another alert. It does not replace the two-device Secure Coms test.

Native full-backup metadata can include saved Wi-Fi/Bluetooth and USB board profiles. Existing backup files remain readable. Older Python versions ignore the additional profile metadata when importing a new backup, so they do not restore those profiles. Preview credentials remain temporary, and its backup/restore workflow is not yet qualified for user data.

Before the candidate selects a first migrated or fresh profile, it writes a local credential-recovery copy protected by Windows for the current account. The candidate Settings page can restore such a copy after confirmation, saves the current credentials first, and closes the app afterward. This local recovery cannot replace a password-protected full backup for moving to a different PC. Synthetic tests check protection, restore and rejection of a damaged copy; the candidate path still needs production qualification.

The candidate selects an independent Windows credential namespace at startup. It checks the legacy profile lock before copying, creates an encrypted recovery snapshot, rejects conflicting entries, resumes matching partial copies, and commits the selection only after verification. Synthetic tests cover existing and fresh profiles, conflicts, locked sources, and later independent edits. Preview 0.1.1 shared the legacy credentials; newer previews use the independent namespace. Real-profile migration and the legacy upgrade path require further qualification.

Run the synthetic and loopback checks with `dotnet run --project "MeshCore Windows/MeshCore.Windows.Core.Tests"` from the repository root. The credential test briefly creates and removes a randomly named test credential. No radio or user profile is accessed by these checks.

The opt-in `--live-map-test` argument downloads a very small real map area into a temporary directory, validates and selects the resulting PMTiles file, and deletes the temporary files. It does not change the user's map selection. This live test passed on the development PC; service availability and larger downloads can vary.

Wi-Fi discovery listens for replies while sending probes, including early replies from fast devices. Its opt-in `--live-discovery-test --address=<test-board-ip>` check passed against the spare V3; loopback tests also cover replies arriving during the scan.

Before switching users, the replacement must support the current Wi-Fi, Bluetooth and USB transports; every desktop feature; radio flashing and updates; secure credentials and backups; and existing local settings, messages and maps. Validate migrations against copies, preserve rollback, and test with actual hardware. Measure the complete application process tree and compare equivalent workloads: replacing the Python host alone will not necessarily reduce WebView memory.
